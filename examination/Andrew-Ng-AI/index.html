Course 01

AI Prompting for Everyone
面向所有人的提示词课。三个模块：查找信息、思维伙伴、多模态与代码。它真正教的不是模板，是判断力——判断这件事该用哪种方式、该给多少信息、该不该让它自己去找。

核心：从「怎么问」到「怎么合作」

2026 年我们用 AI 的方式，跟 2022 年 ChatGPT 刚出来时已经完全不一样了。

2022 年的玩法是「怎么问」——角色扮演、思维链、魔法咒语。2026 年的玩法是「怎么合作」。

吴恩达给了一个贯穿全课的心智模型：AI 是一个极其聪明、积极性很高、但完全不了解你情况的应届毕业生。 你带这样的新人会怎么做？给清楚的任务、给足背景、给判断标准、允许他反问、事后检查。这套做法就是现在所谓的提示词工程。

这一门如果只记一句

你给的方向越清楚，它干得越好；你让它挑毛病，它就挑；你让它去查，它就查。问题是你有没有明确要求。

1 · 查找信息

1.1 先判断：它脑子里有没有

这一步最多人跳过，但它决定后面所有操作。AI 的知识有两个来源：

  • 预训练知识 —— 训练时「背下来」的，不联网也在，但有截止日期
  • 实时信息 —— 必须联网才拿得到

判断方法只有一句：这件事有没有「随时间变化」的属性？

问题判断做法
光合作用的原理是什么不会变直接问，别联网
昨天的发布会说了什么天天变必须联网
C# 的 async/await 怎么用基本不变直接问
某个库最新版本 API 变了没会变联网，且指定查官方文档

新手和高手的分界线就在这。新手把所有问题都丢给联网搜索，结果慢、还容易抓到垃圾信息；高手先用一秒判断，该直答就直答。

1.2 三种方式的取舍

方式适用速度准确度
模型自带知识常识、原理、历史最快高（有截止日期）
Web search最新事实、简单核查快较高
Deep research复杂问题、需多源交叉验证慢最高

1.3 Web search 的关键：不是「搜了没」，是「搜了哪」

光打开联网开关不够。不限定来源，AI 会从博客、论坛、内容农场抓东西——看起来有出处，其实是二手转述。

三个可操作动作：

  1. 指定来源层级：优先官方文档、政府官网、行业报告，明确排除什么
  2. 要求附链接：把结论和出处绑在一起，你才能自己核
  3. 要求交叉：让它在立场不同的来源之间对比，而不是自行调和
模板 · 带来源的调研
请联网搜索【主题】，优先采用官方文档与权威机构来源，避免博客和论坛。每一条结论后附上具体来源链接。如果不同来源说法冲突，请分别列出，不要自行调和。

1.4 Deep research 什么时候用

它不是「更强的搜索」，是会自己追问自己的搜索：拿到初步结果后，根据缺口自动发起下一轮查询，多轮之后汇总成报告。

该用不该用
需要多角度论证的话题简单事实核查（浪费额度和时间）
信息零散且专业的领域你自己都不确定问题边界时
你要一份能拿出去的报告一句话能答完的问题

判断标准：答案能写成一页纸以上的结构化内容，用 deep research；一句话能回答，别用。

配套练习：同一个 prompt 跑不同模型

模块 1 有个练习，做的事很简单：把同一段 prompt 丢给几个不同模型，对比输出。这个练习看着朴素，价值在于它让你发现两件事——

一是换模型能带来多大差异。很多「prompt 没调好」的问题，其实是模型选错了；反过来，有些你以为必须换模型的问题，改 prompt 就能解决。

二是每个模型有不同偏好。有的偏爱结构化输出，有的偏爱长段落，有的对否定指令（「不要做 X」）服从度差。知道这些偏好，你写 prompt 时会自然适配。别把那句「用最强的模型」当成解决方案，那是最后手段，不是第一手段。

2 · 思维伙伴

全课最值钱的部分。前面教你怎么拿到信息，这里教你怎么用它思考。

2.1 Context：它不是肚子里的蛔虫

大多数人给指令像跟老朋友说话——省略大量背景，指望对方能猜。AI 猜不出来，它只会用最通用的方式回答你。

上下文三要素：

  1. 角色 —— 它是谁（资深架构师 / 编辑 / 挑剔的投资人）
  2. 任务 —— 做什么，产出什么形态
  3. 约束 —— 字数、格式、受众、风格、不能做什么
比任何模板都好用的自检法

「如果我是一个完全不了解背景的陌生人，仅凭我这句话，能把这件事做对吗？」

做不对，就说明你缺背景。这一秒就能用，不需要记模板。

2.2 Sycophancy：最大的问题不是出错，是讨好你

Sycophancy（迎合讨好）指模型天生倾向于同意你、肯定你、顺着你的方向说，即使你的前提是错的。

你问「这个方案好不好」，它大概率说「很好」——不是它判断过，是它在配合你。这对你毫无价值。

四种破解方式，强度递增
  1. 明确要求批评：「请指出至少三个问题，不要客气。」
  2. 切断礼貌压力：「不要为了让我舒服而妥协，我需要真实的判断。」
  3. 设定对立角色：「你现在是一个极其挑剔的投资人，请从成本角度最严厉地批判这个方案。」
  4. 改造提问方式 —— 最根本的一条：不要让问题里带答案
引导性提问（只会得到附和）中立提问（能得到信息）
这个方案是不是有问题？这个方案最大的风险在哪？
我觉得 A 更好，你觉得呢？客观对比 A 和 B，指出各自致命缺陷
这个模型是不是被阉割了？有哪些可验证的指标能区分完整版和降级版？
我这个想法能成吗？这个想法在什么条件下会失败？
最后一行是真会发生的事

你带着结论去问，它就会把结论还给你。问「是不是被阉割了」，它会顺着说「是的，确实有阉割」。要拿到真实答案，得把问题改成中立的、可验证的形式。

2.3 头脑风暴：第三步才是重点

大多数人用 AI 想点子是这样的：给主题 → 让它吐 10 个 → 挑一个。这是最低效的用法。

  1. 先发散，而且要显式要求「半疯狂的选项」「其中 5 个常规，另外 5 个必须大胆甚至有点疯，不用考虑可行性。」—— 这一句会明显拉开差距，因为模型默认倾向于给「安全」的答案。
  2. 选方向深入「我对第 3 个方向感兴趣，沿这个方向再给 3 个具体方案。」
  3. 让它挑刺「这几个方案最大的风险是什么？有没有我没考虑到的问题？」

第三步最容易被跳过，也最值钱。前两步给你素材，第三步才帮你筛掉错误。

2.4 写作：先搭骨架，再填血肉

为什么必须先出大纲：直接让 AI 写整篇，你之后改一个地方，其他地方不会联动。先生成大纲，你调的是结构——改一处，整个框架跟着动。

工作流writing flow
// 顺序不能乱，第二步必须你自己做
给上下文（角色 / 受众 / 论点）
  → 让它出大纲
  → 你调结构        // 这一步 AI 替不了
  → 按大纲逐段展开
  → 让它扮苛刻编辑提反馈
  → 去 AI 味润色
AI 文本的四个明显特征
  • 爱用大词：delve、nuanced、robust、comprehensive 出现频率异常高
  • 排比三连：「A、B 和 C」这种三件套句式
  • 形容词堆叠：highly insightful、robustly structured
  • 固定句式：「不是 X，而是 Y」
去 AI 味的四个方法
  • 给它一个「声音」：给几段你自己写的样本，让它学你的句式
  • 先让它写，你改语气，再让它润色（不要直接用第一版）
  • 加主观视角：用「我最近发现……」这种口吻
  • 反过来用：让它识别自己写的文本里有哪些 AI 特征，然后针对性删
AI 是草稿助手，不是最终输出。

2.5 Reasoning：什么时候该让它想久一点

现在的模型普遍有「思考档位」——低、中、高，有些还有更高的一档。这个开关不该一直开着，也不该一直关着。

核心判断只有一句：这题换成人来做，需不需要坐下来想十分钟？

该让它多想别让它多想
多约束权衡（预算、时间、偏好互相冲突）格式转换、翻译、改写
重要且不可逆的决定简单事实查询
题目里埋了陷阱，需要先识破批量处理同一类任务
需要先算再答，算错代价高创意发散（想太久反而收敛）
两个反直觉的点

思考不是越久越好。在创意发散和格式规整这两类任务上，高思考档位反而容易绕远——它会给你一个更「周全」但更平庸的结果。

思考也计费。思考用的 token 通常按输出计，所以高档位的成本可能是低档位的好几倍，延迟也明显更长。这不是免费的推理能力。

2.6 AI desktop apps：让它直接读你的文件

桌面端的 AI 应用和网页版最大的区别，不是界面，是它能碰到你本地的文件。你不需要把代码复制粘贴进去，直接把目录指给它。

这个能力对你特别直接：让 AI 桌面端读你的 Unity 工程目录，它能同时看到 Assets/Scripts 的脚本、ProjectSettings 的配置、Packages/manifest.json 的依赖，然后回答「这个项目用了什么渲染管线」「这个报错可能跟哪个设置有关」这类问题。这些答案靠粘贴代码是拿不到的，因为它需要跨文件看关系。

一个额外的好处

给了目录之后，AI 生成的代码会自然地贴合你项目的命名习惯和现有结构，而不是给你一套「教科书式」的写法。上下文不只是数量问题，也是「贴着你的实际情况」的问题。

注意权限：桌面端读本地文件意味着它能读到你不希望它读的东西。只授权具体目录，不要授权整个用户目录。

2.7 AI critique：让它当审稿人

这是一节独立的内容，因为它和 2.2 的 Sycophancy 是同一件事的两面：2.2 讲它为什么不说真话，这里讲怎么让它说真话并有用。

多数人让它「看看这段写得怎么样」，拿回的是「结构清晰、表达流畅、可以考虑补充一些例子」——这不是批评，这是礼貌。

让它审得有用的四个条件
  1. 先给标准，再让它审。不给标准，它按通用标准评，结论必然是空话。标准可以是：这段要说服谁、最重要的三个信息是什么、字数限制多少。
  2. 要求分级。「按致命 / 重要 / 可选三档列出问题」，这样你才知道哪些必须改。
  3. 要求给修改方案，而不只是指出问题。「每条问题后面附一个具体的改法」，否则你还是不知道该怎么做。
  4. 改完再审一轮。第一次批评往往只抓到表层，改完再让它看，能挖出更深的问题。
为什么这一节对你最重要

这个能力可以直接迁移到审查代码。它比「让 AI 写代码」更有价值——写出来的东西你得看得出来对不对，而「看得出来」正是最缺、也最难补的一环。审稿的能力，和审代码的能力，是同一套东西：给定标准、分级、要改法、多轮。

模板 · 结构化审稿
请按以下标准审查下面的内容： 1) 目标读者是【谁】； 2) 必须传达的三个信息是【什么】； 3) 篇幅限制【多少】。 按「致命 / 重要 / 可选」三档列出问题，每档标出具体位置。每条问题后面附一个具体的修改方案，不要只指出问题。如果某处其实没问题，也请说明为什么，不要为了凑数而挑毛病。 【内容】

3 · 多模态与代码

3.0 「多媒体」到底包括什么

课程这里的范围比很多人想的宽：图片、PDF、截图、表格、文档、音频，都能作为输入的一部分。关键不在于它能读什么，而在于这些都占上下文额度。

最容易被忽略的约束

一张高分辨率图片消耗的额度，可能相当于几千个字。所以「一次塞十张图」往往不是模型读不懂，是额度被图吃光了，它没空间思考。表现出来就是：回答很浅、漏掉你明确说过的要求、或者干脆忘了前面聊的内容。

遇到这种情况，先减图或降分辨率，而不是怀疑模型能力。

3.1 看图：三个层次

层次做法
基础读图里的文字（截图转表格、笔记转 Markdown）
进阶基于图给建议（这张装修图怎么提升空间利用率）
高手图 + 文字一起给，拼出完整上下文（这是报错截图，结合我刚才的操作步骤判断原因）
两个容易忽略的限制

细节会被漏掉。图越复杂，AI 越可能忽略角落里的东西。重要细节要在文字里点出来。

多图比单图准。给正面、侧面、细节三张，比给一张全景效果好得多。

3.2 生图：描述越具体越接近

三层递进
L1 画一只猫                          → 普通
L2 橘猫坐在窗台，侧光，水彩，暖色调      → 有氛围
L3 ……画面要让人联想到周日下午的慵懒感   → 有情绪

核心只有一条：具体到「光线、材质、风格、情绪」，而不是只描述物体。

3.3 数据分析：不用写 Python，但要说清业务问题

把 CSV 丢进去，让它理解字段、做探索、出图、给推断。门槛不在代码，在于你能不能把业务问题描述清楚。

必须养成的习惯

让它把计算用的代码展示出来并解释。理由有两条：你能验证它算得对不对，也能跟着看懂处理逻辑。不展示代码的分析结果，不要直接拿去用。

3.4 零代码建东西：说清三件事

不用会编程也能做出网页、小游戏、小工具。关键在于把需求拆成三句：

WHAT
有什么
元素清单
LOOK
长什么样
视觉与布局
ACT
点完发生什么
行为与反馈
模板 · 零代码建原型
做一个网页版番茄钟：25 分钟倒计时，界面简洁深色主题。开始/暂停按钮在下方，结束后有声音提醒，另加一个设置按钮可以自定义时长。请给完整的 HTML/CSS/JS，并说明每一部分在做什么。

然后就是迭代：改颜色 → 加功能 → 调布局。你的角色是产品经理，不是程序员。

→ 这一节你会 C#，价值有限。但「三句话描述清楚需求」这个框架，在让 AI 写 Unity 脚本时照样适用。

三个模块各配一个动手练习

这门课的作业不多，但每一个都指向一个具体能力。想省时间的话，只看这三件事要你做什么：

模块练习内容它想让你获得什么
1 把同一段 prompt 丢给几个不同模型，对比输出差异 知道「换模型」能改变多少，以及各家的偏好
2 用 AI 做一轮头脑风暴，再让它以审稿人身份批评结果，然后改一版 体会「发散 → 挑刺 → 修订」这个循环，而不是只做第一步
3 用纯文字描述做出一个小应用，并迭代几轮 知道「描述需求」和「改需求」是两件不同的事

4 · 五条原则：2022 vs 2026

#原则2022 的做法2026 的做法
1知道它知道什么所有信息都塞进去先判断它是否已有，再决定搜不搜
2给足上下文一句话指令角色 + 任务 + 约束 + 示例
3迭代问一次就结束问 → 看 → 追问 → 改 → 再问
4让它说真话它说什么信什么明确要求反对意见和批评
5它是助手全权交给它它出初稿，你把关

5 · 自检清单

每次用 AI 前过一遍，九条，三十秒。

  • 我要的东西说清楚了吗？产出形态是什么？
  • 这件事它脑子里有吗？还是必须联网？
  • 要联网的话，我说了优先查哪些来源、要附链接吗？
  • 背景给够了吗？（用「陌生人测试」验一遍）
  • 输出格式说了吗？（字数、结构、风格、受众）
  • 我有没有让它提反对意见？
  • 我的提问里是不是已经暗示了答案？
  • 结果我自己核过了吗？（尤其是数字和引用）
  • 这是草稿还是终稿？我改过吗？

6 · 你的缺口诊断

这段不是课程内容，是按你在对话里的实际提问方式推的。不准就忽略。

最大缺口
Context —— 给的信息太短

「地址」「哪些是适合我的」「这 2 门有什么区别」——这种问法在人跟人之间没问题，因为对方会追问；但 AI 不会追问，它按最通用的假设补空，于是给你「正确但不对味」的答案。
补法：用陌生人测试。问之前想一秒——完全不了解我的人，看到这句话能答对吗？

最大缺口
Sycophancy —— 问题里带了结论

问「V4.1-Flash 是不是阉割版」，问题里已经写了「阉割」这个结论。这种问法下任何模型都会顺着说「是的」。
补法：改成验证型——「有哪些可测量的差异能区分完整版和降级版？」

中等缺口 · 约 20 分钟
搜索纪律 + 让 AI 挑刺

你大概有联网搜索的习惯，但未必有「指定权威来源、要求可核」的纪律；头脑风暴的第三步（让它挑刺）大概率跳过了。这两个加起来二十分钟能改过来。

可以完全跳过
模块 3 的零代码建站 / 模块 1 的基础概念

你会 C#，不需要「用嘴说话做网站」；预训练知识和联网的区别你显然清楚。

对你有额外价值
2.4 的 AI critique —— 让它当代码审稿人

这个能力可以直接迁移到审查你写的 Unity C# 代码。比让它写代码更有价值——它写的东西你得看得出来对不对，而「看得出来」正是你现在最缺的一环。

Course 02

Agentic AI
从「一次问答」走向「多步执行」。五个模块、31 节：先讲清楚什么叫 agentic，再拆四种设计模式，最后用大段时间讲评估——这部分是大多数教程根本不提的。

核心：agentic 是程度，不是开关

这门课开场就纠正了一个常见的错误争论：「这是不是一个真正的 Agent？」这个问题本身问错了。

吴恩达的观点是：应该看的是系统在多大程度上是 agentic 的——AI 能自主规划、使用工具、迭代改进到什么程度。这个视角一转，讨论就从「是不是」变成了「有多少」，也就能比较了。

为什么这个区分重要

如果你以为 agent 是个二元状态，就会陷入「我的项目算不算 agent 项目」这种没有产出的纠结。如果你把它看成一条谱系，问题就变成「我这一步该交给它多少自主权」——这是可以设计、可以调的。

1 · 自主程度谱系

L0
单次生成
一问一答，不给修改机会
L1
固定流程
步骤写死，模型只填空
L2
自评循环
生成后自己检查再改
L3
自主编排
自己决定用什么工具、走几步

课程里用写作来对比这件事，非常直观：

同一个任务，两种做法
// 非 agentic：一次成型，不许回头
"写一篇关于 X 的文章，从头到尾一次写完，不许用退格键。"
        ↓ 结果：结构经常崩，越写越偏

// agentic：允许中间停下来判断
写大纲 → 我需不需要查资料？ → 写初稿
     → 哪几段要改？ → 修订
     → 够了吗？ → 交付

差别的本质不是模型更强，是允许它中途做判断。这也是为什么 agentic 系统在长任务上明显占优——长任务必然出错，区别在于出错了有没有机会改。

1.1 它擅长什么，不擅长什么

优势原因
长任务质量更高中间可以停下来检查，错误不会一路累积
能处理「步骤数事先不确定」的任务可以根据中间结果决定要不要多走一步
错误可以局部修复知道哪一步坏了，只重跑那一步，不用整体重来
能接外部系统通过工具拿到模型权重里没有的信息
代价是真实的，不是理论上的

延迟成倍增加——每一步都要等一次模型响应。成本成倍增加——步数乘 token。最麻烦的是调试变难：单次问答错了你能看输入输出，多步系统错了你要先定位是哪一步。

所以判断标准不是「agentic 更先进」，而是这个任务的复杂度是否真的需要它。一个问题一句话能答的事，套上 agent 只会更慢更贵，还更不稳。

1.2 典型应用场景

课程列举的场景有个共同特征：答案不在模型权重里，且需要多步才能拿到。

  • 客户支持：查订单 → 判断政策 → 决定是否退款 → 回复。每步依赖上一步结果
  • 编码：读代码 → 定位问题 → 改 → 跑测试 → 根据失败信息再改
  • 深度研究：初步检索 → 发现缺口 → 补检索 → 交叉验证 → 成稿
  • 数据分析：理解字段 → 探索 → 发现异常 → 追查原因 → 出图

反过来说，单步、答案明确、不需要外部信息的任务，不该做成 agent。这是最常被违背的一条。

1.3 任务分解：设计的起手式

课程里有一节专门讲这个，位置在四种模式之前——因为它确实是设计的第一步：你还没有模式可选的时候，先得知道任务由哪几步组成。

  1. 写成一个步骤序列按「一个熟练的人会怎么做」写下来，别按「模型应该怎么做」写。人对流程的理解通常比模型可靠。
  2. 标出最容易出错的那一步不用平均用力。一个五步流程里，通常只有一两步是真难点，其余是搬运。
  3. 对那一步加防护这一步才轮到用模式：需要重看 → 反射；需要外部信息 → 工具；步骤不确定 → 规划。
  4. 其余步骤尽量写死能固定流程的不要交给模型判断，固定流程更便宜也更稳。
分解粒度：太粗没用，太细会炸

太粗——「分析这份数据然后给建议」，模型不知道从哪下手，每步都可能跑偏。
太细——把「读文件」拆成「打开句柄 / 逐行读 / 关闭句柄」，token 成本翻十倍，收益为零。
合适的粒度：每一步都是一个「可以独立判断对错」的单元。如果某一步你没法说它做对了还是做错了，说明拆得不够；如果某一步你要写三段话才能描述清楚，说明该合并。

2 · 四种设计模式

整门课的骨架就是这四个。它们不是四个技术，是四种组织循环的方式。

模式解决什么问题什么时候用代价
Reflection
反射		 一次生成的输出质量不够 有明确质量标准、能判断好坏的任务 token 翻倍，延迟翻倍
Tool Use
工具使用		 模型需要读数据、执行动作 答案不在权重里，在外部系统里 要处理工具报错、参数幻觉
Planning
规划		 任务太长，一步做不完 步骤数量事先不确定 计划本身可能错，要能推翻重来
Multi-Agent
多智能体		 单上下文装不下，或需要不同角色 子任务之间可以并行或分工 通信开销大，调试困难
一个常见误用

这四个模式是「当问题出现时才用」，不是「架构上先铺好」。很多项目一上手就搭多智能体，结果发现单 agent 加个好工具就够了。复杂度是最后才加的东西，不是起点。

3 · 反射 Reflection

3.1 它为什么有效

一次生成时，模型没有机会看到自己的输出。它写的时候不知道后面会写成什么样，所以结构性问题会一路累积。

反射把这个过程拆成两段：先产出，再以「读者」身份重看一遍。模型在第二次看的时候，能发现第一次写的时候发现不了的问题——这不是玄学，是因为上下文变了。

3.2 关键是「反馈从哪来」

这一点课程里讲得很实在，也是最多人做错的地方。反馈有三种来源，可靠性完全不同：

反馈来源可靠性说明
模型自评低同一个模型审自己，容易自我肯定
另一个模型 / 角色审中换了视角，但仍可能迎合
外部确定性信号高编译器报错、单元测试结果、代码执行输出、schema 校验
这一节最该记住的一句话

能拿到确定性反馈时，永远优先用确定性反馈。代码能编译就是能编译，测试过了就是过了，这些不需要模型判断。反射模式真正的威力在于「把确定性信号接进循环」，而不是「让模型自己反省」。

3.3 怎么验证反射有用

课程在这里做了一个很关键的示范：不能凭感觉说「加了反射之后变好了」。要用同一组测试输入，跑两种配置，对比分数。

这一点跟模块 4 的评估是连着的——如果没有评估能力，你根本不知道反射是在提升质量，还是只是在增加 token 消耗。

3.4 示意图：图表生成工作流

课程用一个「生成图表代码」的例子演示：模型生成绘图代码 → 执行 → 拿到报错或图形 → 根据结果修正。这是反射 + 工具执行的组合，也是最能说明「确定性反馈」价值的例子——代码跑不跑得起来，是机器判断的，不是模型说的。

4 · 工具使用 Tool Use

4.1 工具是什么

一个工具 = 一个函数 + 一段描述。描述的质量直接决定调用准确率，这一点被严重低估。

模型看不到你的代码实现，它只能看描述来决定「该不该调、传什么参数」。描述写得含糊，它就会乱调或者不调。

写好工具描述的三条

1. 说清「什么时候用」，不只是「这个函数做什么」。
2. 参数要写边界：格式、取值范围、必填还是有默认值。
3. 明确失败行为：出错返回什么，让模型知道该怎么处理。

4.2 工具语法：参数怎么定义

工具定义里有两套信息，分工不同，混在一起就会出问题：

  • 描述（description） —— 给模型看的，决定「该不该调这个工具」
  • 参数结构（schema） —— 给模型看的，决定「怎么传参」，同时也是运行时校验依据
要素该写清什么不写的后果
类型string / number / bool / 数组 / 对象传成字符串 "10" 而不是数字 10，直接报错
必填与否哪些必须给，哪些有默认值漏传必填项，或该用默认值时乱填
取值范围枚举值、上下限、格式（如日期、路径）传了非法值，工具端才炸
嵌套结构对象里有哪些字段层级搞错，参数结构对不上
一个实用原则

能让 schema 约束的，别靠描述去说。「参数必须是 low/medium/high 之一」这句话写在描述里，模型可能记不住；写成枚举，它就只有三个选项。schema 是硬约束，描述是软提醒——能用硬的别用软的。

参数名怎么起

这条看起来是小事，实际影响很大：参数名本身就是提示信息。path 不如 script_relative_path 明确；n 不如 max_results 明确。模型靠名字猜语义，模糊的名字会导致填错。

4.3 代码执行

让模型写代码然后执行，是工具使用里最强也最危险的一种。它把「模型猜测结果」变成「机器给出结果」。

课程里强调了沙箱：执行环境要隔离，文件系统、网络访问都要限制。这不是谨慎过度——模型生成的代码你事先并不知道它会做什么。

4.4 MCP

MCP（Model Context Protocol）解决的是「工具接入的标准化」：以前每接一个系统都要写一套适配，现在把工具暴露成统一的协议，任何支持 MCP 的客户端都能用。

它的价值在于复用：你写一次工具服务，Claude、IDE、你自己的 agent 都能接。对本地工具链（读文件、查数据库、调内部 API）尤其合适。

5 · 评估与误差分析

这是全课最值钱的部分

如果这门课只允许留一个模块，就是这一块。前面讲的是「怎么搭」，这里讲的是「怎么知道搭得对不对」。而绝大多数教程在讲完怎么搭之后就结束了。

5.1 为什么 agentic 系统更难评估

单次问答对错分明，多步系统不行：每一步都可能出错，而且错会传递。最后结果不对，你无法从结果倒推出是哪一步坏掉的。

所以 agentic 的评估必须是分层的：整体评估告诉你「有没有问题」，组件级评估告诉你「问题在哪」。

5.2 误差分析：不要凭感觉改 prompt

这是整个模块最有操作性的方法。流程如下：

  1. 攒失败样本一批真实输入跑一遍，把输出不理想的都挑出来。不用多，二十条就够看出模式。
  2. 给每个失败打标签按失败类型分类：是没查到信息？查到了但没用对？格式不对？还是逻辑跳跃？
  3. 数频次，排序哪一类出现最多，就先修哪一类。这一步是重点——大部分人凭印象改，改的是自己印象最深的那一条，而不是出现最多的那一类。
  4. 只改一个变量，重跑同一批样本改完立刻用同一批输入验证，看这一类失败是不是真的减少了。
  5. 确认没有引入新问题修 A 类的时候经常把 B 类弄坏。所以每次都要跑全量，不是只跑修的那几条。
最常见的错误做法

看到一个失败案例 → 立刻改 prompt → 感觉好多了 → 结束。
问题在于：你不知道这次改动是只修好了这一条，还是把所有类似情况都修好了，还是顺带弄坏了别的。没有测试集，这三种情况看起来一模一样。

5.3 组件级评估

把系统拆成几个可独立评判的环节，分别评估。比如一个 RAG 系统：检索质量、答案忠实度、格式合规，三件事要分开测。

理由很实际：整体分数掉了 10 分，可能是因为检索退化了，也可能是生成变差了。不拆开，你改不对地方。

5.4 延迟与成本优化

agentic 系统的成本是乘法关系：步数 × 每步 token × 单价。所以要优化的地方有三处：

维度手段
步数能不能合并步骤；能不能在简单输入上走短路
每步 token上下文裁剪；缓存重复部分；不要把整个文档history每次重发
单价分级用模型：难判断的用强的，格式化这类机械活用小的

顺序很重要：先评估质量，再优化成本。反过来做，你会为了省钱把质量削掉，而且不知道削掉了多少。

5.5 发现问题之后：四种手段的优先级

误差分析告诉你「哪一类错最多」，接下来是选手段。这里有明确的成本顺序，很多人一开始就用最贵的那一种。

顺序手段适用症状成本
1改指令：补约束、加示例、拆开要求输出格式不对、漏掉要求、理解偏了最低
2补工具：加检索、加校验、加计算信息不足、算错、凭猜中
3拆步骤：一步拆两步，加中间检查任务一长就崩、后半段跑偏中高
4换模型：用到更强的前三招都试过仍然不行最高
最常见的错误：直接跳到第 4 步

结果不对就换更强的模型——这是最省事也最贵的做法。问题在于它掩盖了真实原因：如果是提示不清导致的，换模型只是碰巧让它猜对了，下次还会错；如果是信息不足导致的，换模型根本解决不了，因为答案不在权重里。

判断方法很简单：这个错，是不是「给它更清楚的说明」就能改？能，就是第 1 步。不能，再看它是不是缺信息。

5.6 完整开发流程

课程最后把整个方法收成一个循环。这个循环的价值在于：它让「改进」变成可验证的动作，而不是玄学调参。

agent 开发循环
// 注意第 2 步的位置——它在写代码之前
1. 定义任务：说清成功长什么样
2. 建测试集：20 条真实输入 + 人给的正确答案
3. 搭最小可行版：能用就行，先不优化
4. 跑一遍，记录每条的结果
5. 误差分析：打标签、数频次、排序
6. 只改最频繁的那一类（且只改一处）
7. 全量重跑：确认修好了，且没弄坏别的
8. 回到第 5 步，直到分数够用
第 2 步为什么必须靠前

因为没有测试集，你就只能用「感觉」当标准，而感觉是不可靠的——METR 的实验里，开发者用 AI 之后普遍觉得自己快了 20%，实测是慢了 19%。

测试集不需要大。二十条真实的输入加人工答案，就够你判断每次改动是变好还是变坏。这件事花两小时，能省掉后面几十次盲改。

6 · 规划与多智能体

6.1 规划：让模型先出计划再执行

规划模式的核心动作很简单：先让它把步骤列出来，再按步骤执行。收益有两个——

  • 计划可以被人（或另一个模型）先审一遍，错了在执行前就能发现
  • 执行过程中可以对照计划检查进度，不至于跑偏了还不知道

课程里还演示了结合代码执行的规划：计划不是纯文字，而是可以执行的步骤，每一步的中间结果都可以被验证。

6.2 多智能体：真正解决的是上下文问题

很多人以为多智能体是为了「让不同角色协作」，但更根本的原因通常是单个上下文装不下：一个 agent 既要读大量资料又要做判断，很快就满了。

拆成多个 agent，等于把上下文分片。但代价是通信——agent 之间的信息传递是有损的，传过去的东西对方不一定理解得和你一样。

6.3 通信模式

模式形态适合
顺序 sequentialA 的输出给 B流水线，步骤明确
并行 concurrentA、B 同时跑，结果合并子任务独立，要速度
移交 handoffA 判断该由 B 处理，直接转交分诊、路由
群聊 group chat多个 agent 在同一对话里讨论需要多方论证
多智能体最容易失败的地方

不是模型不够聪明，是信息在传递中丢失。A 觉得已经说清楚了，B 收到的信息不足以做判断，于是 B 开始猜。表现出来就是「每个 agent 单独看都对，串起来就跑偏」。

所以多智能体的关键工程问题是接口设计——传什么、用什么格式传、传不过去的时候怎么报错。这和微服务之间的问题一模一样。

7 · 换算成 C#

课程用原生 Python 从零实现，不绑框架。好处是你学的是模式本身，坏处是要自己换算。下面是四个模式的落点。

先确认一件事

Semantic Kernel 已进入维护模式（只修 bug，不加新功能）。新项目用 Microsoft Agent Framework（NuGet 包 Microsoft.Agents.AI），底层用 Microsoft.Extensions.AI 的 IChatClient 做 provider 抽象。网上大量 SK 教程在这个时间点已经过时。

课程模式它在解决什么.NET 侧对应
Reflection 输出质量不够，靠重看来提升 没有现成 API。你自己搭循环：writer → critic → writer
Tool Use 需要读数据、执行动作 AIFunction / Function Calling
Planning 任务太长，一步做不完 结构化输出（先吐计划）+ agent 编排
Multi-Agent 上下文装不下，或需分工 Agent Framework 的编排模式：sequential / concurrent / handoff / group chat

上表是概念对应，不是官方命名。具体 API 形态要按当前版本文档确认。

反射循环示意

Reflection.cs示意，非可直接运行
// 关键不是怎么写，是 checker 从哪来
var draft    = await writer.RunAsync(task);
var critique = await critic.RunAsync($"审查以下产出，指出具体问题：\n{draft}");
var revised  = await writer.RunAsync($"按反馈修改：\n{draft}\n\n反馈：\n{critique}");

// 但如果是代码，别问模型对不对——编译一下
var build = Compile(revised);
if (!build.Success)
    revised = await writer.RunAsync($"编译报错如下，请修复：\n{build.Errors}");

第二段才是重点。模型的批评可能不准，编译器的错误不会。这就是课程里反复强调「确定性反馈」的意思——能交给机器判断的，别交给模型判断。

工具定义示意

Tools.cs示意，非可直接运行
// 描述的质量决定调用准确率，不是实现
[Description("读取 Unity 工程中某个 C# 脚本的完整内容。用于分析现有代码结构。"
           + "路径相对于 Assets/ 目录，必须带 .cs 后缀。文件不存在时返回错误信息。")]
static string ReadScript(
    [Description("如 Scripts/PlayerController.cs")] string path)
{
    if (!path.EndsWith(".cs"))
        return "错误：只接受 .cs 文件路径";
    var full = Path.Combine(root, "Assets", path);
    return File.Exists(full) ? File.ReadAllText(full) : "错误：文件不存在";
}

8 · 学习节奏

不要顺着刷完。每看完一个模式，停下来用 C# 实现一遍，再往下看。看吴恩达用 Python 写会产生「我懂了」的错觉，换成 C# 才会暴露真正没懂的地方。

  1. 模块 1（约 30 分钟）只看不写代码。目的是拿到「自主性程度」这个判断标准。
  2. 模块 2 结束后用 C# 实现一个最小的反射循环——让模型写代码 → 另一个角色审 → 改。
  3. 模块 3 结束后给上一步的 agent 接一个真实工具（读本地文件 / 调一个 API）。
  4. 模块 4 结束后给这个 agent 加评估：准备 20 个测试输入，打分，看改动前后的差异。
  5. 模块 5 结束后拆成两个 agent 协作，跑一个真实任务。
第 4 步是关键，也最容易被跳过

大多数人卡在第 3 步就停了——能跑起来就觉得成了。但「能跑」和「跑对」是两件事。第 4 步才是把你从「调 prompt 的人」变成「能交付系统的人」的分界线。

9 · 自检清单

  • 我这一步真的需要自主决策吗？还是固定流程就够？
  • 我的反射循环里，反馈来自模型还是来自机器？
  • 工具描述里写了「什么时候用」「参数边界」「失败返回什么」吗？
  • 我有一批固定的测试输入吗？（没有的话，所有改动都无法验证）
  • 我知道最近一次变差是哪个环节造成的吗？
  • 我是按失败频次排优先级，还是按印象？
  • 这次改动有没有把别的功能弄坏？跑全量了吗？
  • 多智能体之间的接口，信息会不会在传递中丢掉？

Summary

两门课什么关系

它们不是两个选项，是一条线的两段。

Prompting
把一次对话说清楚
→
Agentic AI
把多次对话组织成系统

Prompting 教你「怎么让这一句话得到好结果」。Agentic AI 教你「怎么让一百句话自动串起来还能保证质量」。后者以前者为砖，但多了一件前者没有的东西：评估。

这也解释了为什么 Agentic AI 有一整个模块在讲评估，而 Prompting 里几乎没有——单次对话你自己看一眼就知道好不好，多步系统你做不到。

你的情况：直接上第二门

你已经在用 AI 干活了，Prompting 里大部分内容是「知道但不熟练」。真正要补的只有三处：Context（给足背景）、Sycophancy（问题别带结论）、AI critique（让它审代码）。这三块在 Agentic AI 里会以别的形式再出现一次——模块 4 讲评估时，你必须先知道评审模型会讨好被评的东西。

所以跳过不算漏，只是换个地方补。
