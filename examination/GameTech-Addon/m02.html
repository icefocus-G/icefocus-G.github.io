1 先划清边界：哪些 Unity m09 已经讲了

⚠
坑本篇不是入门。 Unity 课程 m09 已有一个独立的「8- 导航寻路系统」章节，讲了概念、组件字段和面板操作。本篇只补它没展开的三件事：烘焙参数怎么调、寻路代价怎么设、网格怎么在运行时重建。没看过 m09 的话，先回去看那一章，否则这里会跟不上。
主题去哪看本篇是否重讲
NavMesh 概念、与 A* 的关系、系统组成Unity m09 · 01 概述不重讲
Agent 各属性字段的含义（Speed / Stopping Distance 等）Unity m09 · 03 寻路组件不重讲，只讲字段的坑
OffMeshLink 的 Start / End / Cost Override 字段Unity m09 · 04 网格外连接不重讲，只讲跨越的控制权接管
动态障碍的 Shape / Carve 基本概念Unity m09 · 05 动态障碍不重讲，只讲什么场景该开
烘焙参数的实际取值、Areas 代价、路径查询 API、运行时重建本篇m09 基本空白

为什么这些算「空白」：m09 的「02 导航网格生成」一节正文只有几十个字，Bake 页签的七八个参数基本靠截图带过；NavMeshPath、NavMesh.CalculatePath、NavMeshSurface 在那一章里一次都没出现。而这些恰恰是项目里真正会卡住你的地方。

◆
核心顺带把最容易被忽略的一层认知补上：NavMesh 解决的是「在地形上怎么走」，不是「该往哪走」。追击、撤退、巡逻这些决策仍要你自己写状态机；NavMesh 只负责把决策结果变成一个可达的位置。
⚠
坑还有一个版本问题要知道。 m09 讲的是 Window > AI > Navigation 那个面板和它的 Bake 页签，但从 Unity 2022 起、到 Unity 6 已经明确移除：旧的内置 Navigation 窗口不再存在，烘焙改成组件式——装 com.unity.ai.navigation 包，给地形挂 NavMeshSurface，在组件的 Inspector 里点 Bake。所以如果你用的是 Unity 6，按 m09 去找那个窗口会找不到；本篇第 8 节讲的就是这套组件式工作流，包括它带来的运行时重建能力。

2 烘焙参数：m09 只给了截图，这里逐个讲

Bake 页签里的每个参数，本质上都在回答同一个问题：这块地面，一个多大的角色能走过去？ 关键是要意识到参数之间不独立——单独调对某一个，未必对。

参数决定什么调错的后果
Agent Radius烘焙边缘精确度，决定可行走区域离墙留多远偏小 → 卡墙；偏大 → 窄门被封死，整条路断掉
Agent Height决定拱桥、门洞下方能否穿越偏大 → 洞被填成实心，通道消失
Max Slope斜坡超过此角度即视为不可走偏小 → 缓坡也走不上去；偏大 → 陡坡能爬，违反直觉
Step Height台阶小于此值可直接迈上偏小 → 一段楼梯被切成几十块不连通区域
Min Region Area小于此面积的孤立碎片被丢弃设 0 会留下大量走不出去的小岛
Height Mesh生成高度网格，让角色贴合起伏平坦地形开着纯属白烧性能
Generated Off Mesh LinksDrop Height / Jump Distance 自动生成跳落连接开太大 → 角色从该断开的地方"自动跳"，像开了挂
⚠
坑最常见的低级错误是 Agent Radius 填 0。这意味着可行走区域紧贴碰撞体边缘，一点余量都不留，实际跑起来角色会反复和边缘碰撞、卡在墙角。经验值取角色胶囊半径 × 0.9。
→
建议Agent Radius 和 Step Height 是一对：楼梯台阶的高度要小于 Step Height，同时楼梯宽度要大于 2 × Agent Radius，一段楼梯才可能被烘成连续可走面。只改其中一个，楼梯照样断。

3 Areas 与寻路代价

Areas 让同一张地图上的地面具有不同的通行代价。A* 会优先走代价低的区域——这是做「敌人绕开泥地」「NPC 只走人行道」的正解。

Area默认代价典型用途
Walkable1普通地面
Not Walkable—墙、水面、岩浆（永不通行）
Jump2跳跃连接（代价高，非必要不走）
自定义（如 Mud / Road）自定泥地代价调高 → 绕行；大路代价调低 → 优先
C#
// 只允许走 Walkable + Road 两个区域
int mask = (1 << NavMesh.GetAreaFromName("Walkable"))
         | (1 << NavMesh.GetAreaFromName("Road"));
agent.areaMask = mask;

// 运行时临时禁行某个区域（比如桥塌了）
agent.areaMask &= ~(1 << NavMesh.GetAreaFromName("Bridge"));

4 Agent 的四个坑（字段含义见 m09）

Speed / Angular Speed / Acceleration / Stopping Distance 这些字段叫什么、干什么，m09 的 03 节已经逐个列过了，这里不重复。只说四个字段名看起来正常、用起来会出错的地方。

坑一：用 remainingDistance 判断到没到。 它看起来最直观，实际最不可靠——在 pathPending == true 期间返回 Infinity，路径不完整时也没有意义。

C#
// 错误写法：会「有时到了不触发、有时瞬间触发」
bool bad(NavMeshAgent a) => a.remainingDistance <= 0.5f;

// 正确写法：四个条件缺一不可
bool Arrived(NavMeshAgent a)
{
    if (a.pathPending) return false;                 // 路径还在算
    if (!a.hasPath) return true;                     // 无路可走
    if (a.pathStatus != NavMeshPathStatus.PathComplete) return true;
    return a.remainingDistance <= a.stoppingDistance + 0.05f;
}

坑二：改了 areaMask 不生效。 掩码只在下一次寻路时被读取，当前已经算好的路径不会重算。改完必须重新 SetDestination 一次。

坑三：radius 和烘焙时的 Agent Radius 不一致。 运行时的 agent.radius 只影响代理之间的避障推挤，不影响它实际能走哪——能不能走是烘焙时定死的。把运行时 radius 调小，角色不会因此钻进更窄的缝，但会和别的代理挤得更近，表现为穿模。

坑四：avoidancePriority 的方向是反的。 数值 0 是最高优先级，越大越容易被推开。想做一个「不会被杂兵挤开」的 Boss，要把它调到接近 0，而不是 99。

5 路径查询三件套（m09 完全没提）

点击移动、可达性判断、视线预警，都靠这三个静态方法，而不是让 agent 真的跑一遍再观察结果。这是本篇最值得带走的一节——m09 里这三个 API 一次都没出现。

C#
// 1) SamplePosition：把任意点吸附到最近的 NavMesh 上
//    点击地面拿到的点常常不在 NavMesh 上（尤其在斜坡/边缘）
if (NavMesh.SamplePosition(clickPoint, out var hit, 2f, NavMesh.AllAreas))
    agent.SetDestination(hit.position);

// 2) Raycast：判断两点之间有没有被墙/断开阻隔（比物理射线便宜且贴 NavMesh）
NavMeshHit navHit;
bool blocked = NavMesh.Raycast(agent.position, target, out navHit, NavMesh.AllAreas);
if (blocked) Debug.DrawLine(agent.position, navHit.position, Color.red);

// 3) CalculatePath：只算路径不移动，用来做「能不能过去」的预判
var path = new NavMeshPath();
if (NavMesh.CalculatePath(agent.position, target, NavMesh.AllAreas, path)
    && path.status == NavMeshPathStatus.PathComplete)
{
    // path.corners 就是拐点数组，可以用来画路线、算真实路程
    float len = 0f;
    for (int i = 1; i < path.corners.Length; i++) len += Vector3.Distance(path.corners[i-1], path.corners[i]);
}
→
建议做点击移动一定要先 SamplePosition。玩家点的是屏幕射线与地面的交点，边界处经常落在 NavMesh 之外，直接 SetDestination 会得到一个最近但很怪的贴合点，表现为「点这边，人跑那边」。

6 OffMeshLink：画不出跳跃的样子

OffMeshLink 的 Start / End / Cost Override 字段含义在 m09 的 04 节已经讲了。这里解决它没覆盖的真问题：默认行为是让 agent 匀速直线滑过去，所以跳跃看着像平移、爬梯看着像飘。要改观感，必须自己接管这段位移。

接管的关键是三步：进入 link 时关掉 agent 的位姿驱动 → 自己插值或播动画 → 结束后调 CompleteOffMeshLink() 交还控制权。

C#
// 让角色在跨越时播跳跃动画：手动接管 OffMeshLink
void Update()
{
    if (agent.isOnOffMeshLink && !jumping)
    {
        jumping = true;
        var data = agent.currentOffMeshLinkData;
        StartCoroutine(JumpAcross(data.startPos, data.endPos));
    }
}

IEnumerator JumpAcross(Vector3 from, Vector3 to)
{
    agent.updatePosition = false;      // 松开控制权，自己插值
    agent.updateRotation = false;
    float t = 0f, dur = 0.4f;
    while (t < dur)
    {
        t += Time.deltaTime;
        float k = Mathf.Clamp01(t / dur);
        var p = Vector3.Lerp(from, to, k);
        p.y += Mathf.Sin(k * Mathf.PI) * 1.2f;   // 抛物线
        transform.position = p;
        yield return null;
    }
    agent.CompleteOffMeshLink();       // 交还控制权
    agent.updatePosition = true;
    agent.updateRotation = true;
    jumping = false;
}
⚠
坑忘了调用 CompleteOffMeshLink()，agent 会永久卡在 link 上不动。这是 OffMeshLink 最常见的 bug。

7 动态障碍：carve 还是不 carve

可移动的障碍（箱子、路障）有两种处理方式，选错会让性能或行为任一崩掉。

策略做法开销效果
不 carve（默认）只靠 agent 的局部避障绕开低障碍物周围不会挖洞，agent 会贴着挤过去
carve = true在 NavMesh 上真实挖洞高（重新计算局部网格）路径真正绕开，像一堵墙
C#
// 大而少（门、路障）：开 carve 才符合预期
var ob = box.GetComponent<NavMeshObstacle>();
ob.shape = NavMeshObstacleShape.Box;
ob.size = new Vector3(2f, 2f, 2f);
ob.carving = true;
ob.carveOnlyStationary = true;        // 只有静止时才挖洞，移动中不挖
ob.carvingTimeToStationary = 0.3f;   // 停下多久算「静止」

// 小而多（几十个滚来滚去的球）：别开 carve，交给避障
ob.carving = false;
◆
核心判断口诀：大而少 → carve；小而多 → 不 carve。给几十个移动物体开 carve，每帧都在重建局部网格，帧率会断崖式下跌。

8 运行时重建：解开 m09 那条局限

ⓘ
背景m09 的 01 节在讲概念时写过一句局限：「只能在编辑模式下进行烘焙，游戏场景模式下不行」。这句话在旧版 Navigation 面板下是对的，但用 com.unity.ai.navigation 包里的 NavMeshSurface 就可以在运行时重新构建——肉鸽、塔防、建造类这种程序化生成的地图，靠的就是它。

把 NavMeshSurface 挂到场景里，配好 agentType 与要收集的层，之后就能在代码里重建：

C#
using Unity.AI.Navigation;

// 场景里挂 NavMeshSurface，配好 agentType 与收集的层
public void Rebuild()
{
    surface.BuildNavMesh();            // 同步构建，会卡一帧
}

// 更平滑的做法：异步更新，避免卡顿
public void RebuildAsync(NavMeshData data)
{
    var settings = NavMesh.GetSettingsByID(0);
    var src = new NavMeshBuildSource();
    var sources = new List<NavMeshBuildSource>();
    // ... 收集 sources ...
    NavMeshBuilder.UpdateNavMeshDataAsync(data, settings, sources, bounds);
}
时机做法注意
地图生成后一次BuildNavMesh()可接受一次卡顿
局部改动（放一个建筑）只更新该 bounds 内的数据bounds 要算准，否则边缘有洞
每帧变化不要重建，改用 NavMeshObstacle carve重建的开销是毫秒级
⚠
坑不要在 Update() 里调 BuildNavMesh()。它的开销在毫秒量级，一帧调一次等于把帧率钉死。

9 性能与常见坑

  • 别每帧 SetDestination：目标没变就别调，否则每帧重算路径。给追击 AI 加个 0.2s 的节流。
  • agent 数量：几十个没问题；上百个要分帧更新（关 updatePosition/updateRotation，自己按帧分摊移动）。
  • 卡墙角：90% 是 Agent Radius 与 collider 半径不匹配，或 stoppingDistance=0 导致贴脸推挤。
  • 穿墙：agent 的 radius 小于烘焙时的 Agent Radius，会钻进本该不可走的缝隙。
  • 路径 Partial：pathStatus == PathPartial 表示只能到最近可达点。UI 上要区分「到了」和「到不了」。
  • 多场景烘焙：用 NavMeshSurface 的 Collect Objects 选择 Current Object / All / Volume，别漏了动态加载的场景。
  • 导航网格可视化：Scene 视图开 Navigation 面板的 Show NavMesh，排查问题比读日志快十倍。

10 跳出游戏：同一套思路还能用在哪

领域映射关系差异点
AGV / 仓储机器人NavMesh ≈ 可通行栅格地图要处理多机避障与死锁，比游戏严格
室内导航（商场/机场）导航网格 ≈ 楼层平面跨楼层要靠 OffMeshLink 式的连接（电梯/扶梯）
无人机航线3D 空间而非 2D 地面NavMesh 只有 2.5D，真 3D 要用体素/八叉树
地图服务可达性Areas ≈ 道路等级代价实时路况 = 动态代价，等价于运行时改 area cost
ⓘ
背景NavMesh 的本质是「把连续空间离散成带权图 + 在其上跑 A*」。理解了这一层，换到任何寻路问题（包括非空间问题，如任务依赖排序）都能迁移。
