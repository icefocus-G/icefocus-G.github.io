1 为什么 Unity 程序员要懂 C

你不需要用 C 写游戏逻辑，但你会不断遇到只有懂 C 才能解释的现象：为什么 struct 传给 Native 插件后数据全乱、为什么 IL2CPP 下某个反射调用失败、为什么多线程里一个 bool 读写会导致崩溃。

场景为什么需要 C 的认知
IL2CPP 打包C# 的 IL 会被转成 C++ 再编译，泛型与反射会受裁剪影响
Native 插件P/Invoke 传 struct 时，字段顺序与对齐必须与 C 侧完全一致
unsafe / fixed直接操作内存，需要理解指针与 GC 句柄固定
GC 与分配理解堆、栈、值类型的分配位置，才能减少 GC 峰值
ⓘ
背景一个反直觉的事实：C# 的值类型也走栈（或内联在对象里），引用类型走托管堆。这条规则和 C 的栈/堆划分是同源的——理解 C 的模型，C# 的行为就不再是「魔法」。

2 指针：地址、解引用、算术

指针就是一个存地址的整数。所有「指针很危险」的说法，本质都是「你手动算错了地址」。

C
#include <stdio.h>

int main(void) {
    int a = 42;
    int *p = &a;          // p 存的是 a 的地址

    printf("%d\n", *p);   // 解引用：顺着地址取值 → 42
    *p = 100;             // 顺着地址写值 → a 也变成 100

    int arr[5] = {10, 20, 30, 40, 50};
    int *q = arr;         // 数组名退化为首元素地址
    printf("%d\n", *(q + 2));   // 指针算术：跳 2 个 int（不是 2 字节）→ 30
    printf("%d\n", q[2]);       // 等价写法
    return 0;
}
  • 指针算术按类型宽度走：int* + 1 前进 4 字节，char* + 1 前进 1 字节。这解释了为什么「跨类型强转指针再算术」会错位。
  • arr 与 &arr 不同：前者退化为 int*，后者是 int(*)[5]。两者数值相同，加 1 后差 20 字节。
  • NULL 解引用是崩溃第一原因，且往往在很远的地方才炸——所以崩溃栈经常指向无辜代码。

C
void bad(void) {
    int *p = (int *)malloc(10 * sizeof(int));
    // 忘记 free：每次调用泄漏 40 字节，跑久了就 OOM
}

void also_bad(void) {
    int *p;
    { int local = 5; p = &local; }   // local 已随作用域销毁
    *p = 7;                           // 悬垂指针：写到了别人的栈帧上
}

void good(void) {
    int *p = (int *)malloc(10 * sizeof(int));
    if (!p) return;                   // 一定要判空
    for (int i = 0; i < 10; i++) p[i] = i;
    free(p);
    p = NULL;                         // 置空，防止后续误用
}
⚠
坑C 的两大经典崩溃：内存泄漏（malloc 没 free）和悬垂指针（free 后继续用）。前者表现为越跑越卡最终被杀，后者表现为随机位置崩溃——两者都极难定位，所以「谁分配谁释放」必须成为铁律。

4 结构体与内存对齐

这是 C# 与 C 交互最容易翻车的知识点。编译器为了保证 CPU 访问效率，会在成员之间自动插入填充字节（padding）。

C
#include <stdio.h>

struct A { char c; int i; };          // char(1) + padding(3) + int(4)
struct B { int i; char c; };          // int(4) + char(1) + padding(3)
struct C { char a; char b; int i; };  // char+char + padding(2) + int

#pragma pack(push, 1)                 // 强制 1 字节对齐，取消填充
struct Packed { char c; int i; };     // 恰好 5 字节
#pragma pack(pop)

int main(void) {
    printf("%zu %zu %zu %zu\n",
        sizeof(struct A),   // 8，不是 5
        sizeof(struct B),   // 8
        sizeof(struct C),   // 8
        sizeof(struct Packed)); // 5
    return 0;
}
  • 对齐规则：每个成员相对起始地址的偏移，必须是该成员自身大小的整数倍；结构体总大小必须是最大成员大小的整数倍。
  • 因此 sizeof 永远 ≥ 成员大小之和，不能用它来估算「字段加起来多少字节」。
  • 字段顺序影响大小：{char, int} 和 {int, char} 都是 8；但 {char, char, int} 是 8，{char, int, char} 却是 12。
◆
核心结论：跨语言传 struct 时，字段顺序、类型宽度、对齐方式三者必须逐字节一致。少对一项，数据就会错位——而且不会报错，只会安静地算出垃圾值。

5 malloc/free 与 GC 的本质差别

维度C（malloc/free）C#（GC）
谁释放程序员显式 free垃圾回收器自动
释放时机确定，立即归还不确定，等 GC 触发
碎片容易产生外部碎片会压缩（部分 GC 实现）
开销分布分配/释放各自付出分配便宜，回收时集中停顿
典型问题泄漏、悬垂指针、重复 freeGC 峰值卡顿、非托管泄漏

Unity 里你其实同时面对两套：托管堆由 GC 管，Native 侧（纹理、Mesh、NativeArray）要自己 Release。所以「Unity 内存泄漏」通常是非托管资源没释放，而不是 GC 没跑。

→
建议优化 Unity GC 的核心不是「少 new」这种笼统建议，而是：消除每帧的堆分配。用对象池、避免闭包捕获、避免 string + 拼接、用 StringBuilder 或 TMP_Text.SetText。

7 和 Unity 的连接点

四个最实际的连接点。每一个都是「不懂 C 就会踩坑」的地方。

① P/Invoke 传 struct

C#
[StructLayout(LayoutKind.Sequential, Pack = 1)]  // 必须与 C 侧 #pragma pack 一致
public struct Payload
{
    public byte  type;
    public int   value;
    public float weight;
}

[DllImport("mylib")]
static extern void SendPayload(ref Payload p);

// C 侧必须完全对应：
// #pragma pack(push,1)
// typedef struct { uint8_t type; int32_t value; float weight; } Payload;
// #pragma pack(pop)

② unsafe + fixed：把托管数组钉住

C#
unsafe void Process(byte[] data)
{
    // fixed：告诉 GC 这批内存我要直接操作，别搬走
    fixed (byte* p = data)
    {
        Native.Process(p, data.Length);
    }
    // 离开 fixed 作用域后，GC 才能移动这块内存
}

③ IL2CPP 的影响

  • C# 的 IL 被转成 C++ 再编译为原生码，不是解释执行
  • 泛型会为每个值类型实例生成独立代码 → 包体增大，需注意 link.xml 保留
  • 反射受裁剪影响，Assembly.GetTypes() 可能拿不到被裁掉的类型
  • unsafe 代码在 IL2CPP 下正常运行，Mono 下需开启 Allow 'unsafe' Code

④ 值类型的内存位置

情况分配位置
局部值类型变量线程栈
class 的字段（值类型）内联在托管堆对象里，不额外分配
数组元素（值类型）托管堆上的连续内存
装箱后托管堆上新建对象（热点！避免）

8 常见崩溃与排查

现象常见原因排查
随机位置崩溃、栈无意义悬垂指针 / 缓冲区越界写ASan、Valgrind；Unity 里开 Addressables 的泄漏检测
跑久了越来越卡、最终被杀内存泄漏Profiler 抓 Native 内存曲线，看是否单调上升
传 struct 后数据全乱对齐 / Pack 不一致两侧打印 sizeof，逐字段比对偏移
多线程偶发崩溃无锁共享变量用原子操作；加锁范围要小
free 时报 invalid pointer重复 free / free 非堆指针free 后置 NULL；只释放 malloc 的指针
⚠
坑一个隐蔽陷阱：越界写通常不立即崩溃。它悄悄破坏了相邻内存，等到那块内存被使用时才炸，而崩溃栈指向的往往是无辜代码。这就是为什么「加一行日志就好了」的现象真实存在——日志改变了内存布局。
