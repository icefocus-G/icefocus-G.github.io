1 先定表，再写码

计费点做砸的项目，九成不是代码问题，而是表没定清楚就开写：点位散落在各个脚本里、埋点名一个页面一个写法、奖励数值硬编码。等到要调优时，没有任何一处可以集中改。

表一行代表什么关键列
事件字典表一个埋点事件event_key、触发时机、参数、归属模块
计费点表一个可变现点位slot_id、类型（IAA/IAP）、触发条件、频控、奖励、开关
商品表一个可购买商品sku、区域、价格档、内容、是否首充/限时
◆
核心顺序不能反：表 → 埋点门面 → 点位实现 → 看板。反过来做（先写代码再补表），必然出现同一个行为三个 event_key、同一个点位两套奖励配置。

2 标签分类总表

标签是把「行为流水」压成「用户画像」的中间层。分四类就够，别一上来搞几十个维度。

类别例子用途
属性标签设备档位、地区、渠道、安装天数分群基线，做冷启动优化
行为标签日均局数、平均单局时长、失败率、流失关卡找卡点，做难度调优
付费标签是否付费、首充有无、累计付费档、最近付费距今天数分层运营与召回
进度标签最高关卡、解锁系统数、收集完成度定位内容消耗速度
→
建议标签要可回溯计算：能由原始事件重新算出来。如果某个标签是「当场算完就存」，一旦口径改了就永远修不回来。

3 事件字典 + 埋点门面

埋点最怕两件事：名字随性起、调用散落各处。解法是一个门面 + 一份常量表，业务代码只准通过门面打点。

C#
// 1) 事件常量：唯一真相，禁止在业务里写字符串
public static class Ev
{
    public const string LevelStart   = "level_start";
    public const string LevelEnd     = "level_end";     // props: result, level, duration, reviveUsed
    public const string AdShow       = "ad_show";       // props: slot, provider, result
    public const string AdRevenue    = "ad_revenue";    // props: slot, ecpm, currency
    public const string IapPurchase  = "iap_purchase";  // props: sku, price, currency, firstPay
    public const string ShopOpen     = "shop_open";     // props: from
}

// 2) 门面：所有打点唯一入口，统一补公共参数
public static class Track
{
    static ITracker impl = new NullTracker();

    public static void Init(ITracker t) => impl = t;

    public static void Send(string ev, Dictionary<string, object> props = null)
    {
        props ??= new Dictionary<string, object>();
        props["uid"]      = User.Id;
        props["level"]    = User.MaxLevel;      // 公共维度自动补齐
        props["channel"]  = BuildInfo.Channel;
        props["ts"]       = TimeUtil.NowMs();
        impl.Log(ev, props);
    }
}

国内与海外的埋点后端不同（国内多为自建或神策/友盟，海外多为 Firebase / Adjust），差异全部收在 ITracker 的实现里，业务层无感知。

C#
public class FirebaseTracker : ITracker
{
    public void Log(string ev, Dictionary<string, object> p)
    {
        var prm = new Dictionary<string, object>();
        foreach (var kv in p)
        {
            // Firebase 参数值只接受 string / long / double
            prm[kv.Key] = kv.Value is int i ? (long)i
                        : kv.Value is float f ? (double)f
                        : kv.Value?.ToString() ?? "";
        }
        FirebaseAnalytics.LogEvent(ev, prm);
    }
}

public class DomesticTracker : ITracker   // 神策 / 友盟 / 自建
{
    public void Log(string ev, Dictionary<string, object> p)
    {
        SensorsDataAPI.Track(ev, p);          // 支持嵌套与数组
    }
}
⚠
坑跨平台埋点最大的坑是类型不一致：Firebase 只收 string / long / double，把 float 直接塞进去会被静默丢弃或转成字符串，导致看板上全是 0。类型转换必须在适配器里做完。

4 IAA 广告点位清单

休闲游戏的广告收入结构通常是「激励视频为主、插屏为辅、Banner 保底」。点位不是越多越好——插屏太密会直接抬高流失率。

点位类型触发时机频控建议注意
开屏Splash冷启动后首次进入主界面每会话 1 次要有跳过，别做成强插
关卡结束Interstitial结算页出现时≥60s 间隔，前 3 关不弹新手期必须保护
失败复活Rewarded失败结算页每关 1 次核心变现点，务必 SSV
双倍奖励Rewarded胜利结算页每关 1 次转化最高，按钮要显眼
离线收益翻倍Rewarded回归时离线收益弹窗每日 3 次与留存强相关
免费道具/抽奖Rewarded商店/抽奖页每日上限配合进度卡点
主界面 BannerBanner常驻底部—别遮挡操作区，iOS 需注意安全区
◆
核心新手前 3 关不弹任何非激励广告。这是留存与变现的经典权衡点：前期多赚几分钱，换来的是次留下滑，长期 LTV 反而更低。

5 IAP 商品清单与定价对照

SKU类型国内档位海外档位设计要点
remove_ads一次性¥6$0.99最常见的首付费点，转化率高
starter_pack一次性¥6$0.99首充礼包，限购 1 次，价值感要强
coin_small消耗品¥6$0.99基础档，用于比价锚定
coin_mid消耗品¥30$4.99主力档，通常销量最高
coin_large消耗品¥68$9.99大 R 档
battle_pass订阅/赛季¥30/月$4.99/月长期留存与稳定收入
  • 定价不要按汇率换算：国内 ¥6 / ¥30 / ¥68 是习惯档位，海外 $0.99 / $4.99 / $9.99 是习惯档位，两者不是汇率关系
  • 必须有锚定：大包单价要明显低于小包，否则没人买大包
  • 首充只在 1 次：首充礼包的价值感一旦被稀释，后续付费转化会塌
  • 消耗品要能重复买，一次性商品（去广告）买完就没有复购，别指望它撑收入

6 远程配置：改策略不发版

频控参数、点位开关、奖励倍率、AB 分组，全都不该写死在包里。发一版审核要几天，而调优要按小时迭代。

JSON
{
  "version": 12,
  "slots": {
    "inter_level_end": { "on": true, "minIntervalSec": 60, "skipFirstLevels": 3 },
    "reward_revive":   { "on": true, "maxPerLevel": 1, "rewardMul": 1.0 },
    "reward_double":   { "on": true, "maxPerLevel": 1, "rewardMul": 2.0 }
  },
  "experiments": {
    "exp_inter_freq": { "group": "A", "minIntervalSec": 45 }
  },
  "fallback": { "on": true }
}
⚠
坑远程配置必须有兜底：拉取失败就用本地默认值，且默认值要保守（频控更严、开关更少）。否则某次配置服务挂掉，可能给用户连弹 10 个插屏。

7 频控与触发（核心逻辑）

频控不是「加个计时器」那么简单，它要同时管住四个维度：冷却、单局上限、每日上限、全局窗口。少一个就会漏。

C#
public class SlotGate
{
    readonly SlotCfg cfg;
    DateTime lastShow;
    readonly Dictionary<string, int> perSession = new();
    int perDay; DateTime dayAnchor;

    public bool CanShow(string slotId, int currentLevel)
    {
        if (!cfg.On) return false;
        if (currentLevel <= cfg.SkipFirstLevels) return false;

        // 1) 冷却
        if ((DateTime.UtcNow - lastShow).TotalSeconds < cfg.MinIntervalSec) return false;

        // 2) 每日上限（跨天重置用锚点，不用 DateTime.Today 比较字符串）
        if (dayAnchor.Date != DateTime.UtcNow.Date) { perDay = 0; dayAnchor = DateTime.UtcNow; }
        if (perDay >= cfg.DailyCap) return false;

        // 3) 单局/单会话上限
        perSession.TryGetValue(slotId, out var n);
        if (n >= cfg.MaxPerSession) return false;

        return true;
    }

    public void MarkShown(string slotId)
    {
        lastShow = DateTime.UtcNow;
        perDay++;
        perSession[slotId] = perSession.GetValueOrDefault(slotId) + 1;
    }
}
⚠
坑MarkShown 必须在真正展示后调用，不能在「准备展示」时调用。否则广告加载失败也会消耗频控额度，用户点了没反应又没奖励，体验极差。

8 收益回传与归因

想把 LTV 算准，光有「展示次数」不够，必须拿到每次展示的收益（impression-level revenue）。主流聚合平台都提供收益回调。

数据来源用途
广告展示收益MAX 的 OnAdRevenuePaidEvent / AdMob 的 PaidEvent按点位算真实 eCPM，而不是估算
内购订单Apple / Google 服务端收据校验防漏单、防伪造
归因来源Adjust / AppsFlyer / 平台回调算渠道 ROI，决定投放预算
C#
// MAX 的收益回调：每次展示后立即上报，别攒批
MaxSdkCallbacks.Interstitial.OnAdRevenuePaidEvent += (adUnitId, info) =>
{
    Track.Send(Ev.AdRevenue, new Dictionary<string, object>
    {
        ["slot"]     = SlotOf(adUnitId),
        ["network"]  = info.NetworkName,
        ["ecpm"]     = info.Revenue,          // 已经是美元
        ["currency"] = "USD"
    });
};
◆
核心内购必须做服务端校验 + 幂等发货：客户端拿到收据后发给自己的服务器，服务器向 Apple/Google 校验，成功才发货，并以订单号去重。纯客户端校验等于没有校验。

9 指标看板：只看这 6 个

指标口径看什么
ARPDAU日广告收入 + 日内购收入 ÷ DAU整体变现效率
eCPM广告收入 ÷ 展示次数 × 1000广告价值，分点位看
填充率成功展示 ÷ 请求次数广告源是否够，低说明要加源
IVR（激励视频渗透）看激励视频的 DAU ÷ 总 DAU点位设计是否合理
次留 / 7 留次日回访 ÷ 新增变现调优有没有伤到留存
LTV / CAC生命周期价值 ÷ 获客成本能不能放量，<1 就是亏
ⓘ
背景变现调优永远看成对指标：单看 ARPDAU 上涨就加大插屏，很可能次留在跌、LTV 在降。只盯一个数的优化，基本都在透支未来。
