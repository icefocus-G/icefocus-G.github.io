// 性能优化：Draw Call 与合批的量化估算
int dcBefore = 0;
var parts = new (string name, int count, bool sameMat, bool dynamic)[] {
    ("敌兵身体", 60, true,  true),
    ("敌兵武器", 60, false, true),
    ("地面瓦片", 200, true, false),
    ("UI 图标", 40, false, true)
};

foreach (var (name, count, sameMat, dynamic) in parts)
{
    int dc = sameMat && dynamic ? 1 : count;   // 同材质可动态合批，否则一个物件一个 DC
    dcBefore += dc;
    Console.WriteLine($"{name,-10} {count,4} 个  同材质={sameMat,-5} 动态={dynamic,-5} -> {dc,4} DC");
}
Console.WriteLine($"优化前合计 {dcBefore} DC");

Console.WriteLine();
int dcAfter = 0;
foreach (var (name, count, sameMat, dynamic) in parts)
{
    if (sameMat) { dcAfter += 1; continue; }          // 合批后 1 个
    if (name == "UI 图标") { dcAfter += 1; continue; } // 打图集后 1 个
    dcAfter += count;                                 // 材质不同且没打图集，合不了
}
Console.WriteLine($"打图集 + 统一材质后：{dcAfter} DC（降 {(1 - (double)dcAfter / dcBefore) * 100:F0}%）");
Console.WriteLine();
Console.WriteLine("三条硬规则：");
Console.WriteLine("  1) 同屏同类物件尽量共用一个材质/图集，否则合批无从谈起");
Console.WriteLine("  2) SRP Batcher 要求 Shader 变体一致，用自定义 Shader 时最容易失效");
Console.WriteLine("  3) 半透明、Mask、自定义材质会打断合批，能合并就合并");

先度量，再优化

没有目标值的优化都是猜。开工前先定三个指标：目标机型、目标帧率、内存上限。然后用 Profiler 抓一段真实战斗的录制，看三张图——CPU 耗时、GC Alloc、渲染（Draw Call / SetPass / Tris）。

指标健康值（中端安卓）超标先查
Draw Call< 150材质/图集是否统一、UI 是否打断合批
SetPass Call< 60Shader 变体过多、SRP Batcher 失效
GC Alloc（每帧）常驻逻辑 0 B字符串拼接、闭包、装箱、LINQ
三角形数< 15 万LOD 缺失、模型面数

合批的三种机制与失效条件

  • 静态合批：勾 Static 的物体在构建期合并成大网格。代价是包体与内存变大，且不能移动。
  • 动态合批：运行期把小网格合成一个批次。限制严格：顶点数少、同材质、同缩放，现代管线里收益有限。
  • GPU Instancing：同网格同材质、参数走 MaterialPropertyBlock，一次提交画多个。适合草、子弹、成群小怪。
  • SRP Batcher（URP）：只要 Shader 变体一致就自动合，与物体数量无关，但换 Shader/材质参数不兼容就会打断。

GC 与内存

  • 用对象池复用频繁创建的对象（子弹、飘字、列表项）。
  • 纹理是内存第一大户：按需降分辨率、压缩格式选 ASTC、大图用完主动 Resources.UnloadUnusedAssets。
  • 音频走流式（Streaming）而不是全部 Decompress On Load。
  • UI 的 Overdraw 用 Scene 视图的 Overdraw 模式看，半透明叠层是主要来源。

优化顺序建议

先降 Draw Call（收益最直接）→ 再压 GC（消除卡顿尖刺）→ 再降纹理内存（防 OOM）→ 最后才是 Shader 与后处理（画质与性能的取舍）。反过来做通常事倍功半。
